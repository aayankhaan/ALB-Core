ALBCore

The base framework for every ALB plugin on Skyabyss. It gives ALBLevel, ALBSkills and later plugins one shared, tested way to build menus, commands, database tables and per-player data, for Java and Bedrock players.

GUI

Chest menus with pages, per-player items, click actions and locked or item-input slots.

Commands

Kotlin builder on Paper's command API: typed args, subcommands, validators, tab completion.

Database

SQLite or MySQL with HikariCP, async queries, versioned migrations.

Player data

Per-player values stored in YAML, SQLite or MySQL, loaded before join, saved in the background.

Hooks

PlaceholderAPI (%alb_*%), Vault economy, PacketEvents.

Utilities

Colours, messages, items, heads, numbers, sounds, Discord webhooks.

ServerPaper 26.3 (build 252 or newer), Java 25
LanguageKotlin 2.4 (the API is designed for Kotlin; Java can call it too)
Soft dependenciesVault (or VaultUnlocked), PlaceholderAPI, PacketEvents. All optional.
BundledKotlin runtime, HikariCP (relocated). The MySQL and SQLite drivers come with Paper.

Install on a server

  1. Put alb-core-1.0.0.jar into plugins/ and start the server once.
  2. Edit plugins/ALBCore/config.yml: choose database.type (sqlite or mysql), fill in the MySQL login, and pick player-data.storage.
  3. Restart. The console shows the database, the player-data storage and which hooks were found. /albcore info shows the same in game.
Secrets: config.yml contains the database password and Discord webhook URLs. Keep it on the server only and never commit it to git.

If ALBCore cannot connect to the database at startup, it logs the reason and disables itself, so no plugin writes data into the void. Plugins that depend on it must check server.pluginManager.isPluginEnabled("ALBCore") at the start of onEnable, before using any ALBCore class.

Build a plugin on ALBCore

First publish the API jar from the ALB-Core folder:

./gradlew publishToMavenLocal

build.gradle.kts

plugins { kotlin("jvm") version "2.4.21" }

repositories {
    mavenLocal()
    mavenCentral()
    maven("https://repo.papermc.io/repository/maven-public/")
}

dependencies {
    compileOnly("io.papermc.paper:paper-api:26.3.build.252-stable")
    compileOnly("com.aayan:alb-core:1.0.0")
    compileOnly(kotlin("stdlib"))   // ALBCore ships the Kotlin runtime
}

kotlin { jvmToolchain(25) }

gradle.properties:

kotlin.stdlib.default.dependency=false

Do not shade Kotlin into child plugins. ALBCore's API passes Kotlin lambdas around, so every ALB plugin must use the same Kotlin runtime: the one inside ALBCore.

plugin.yml

name: ALBLevel
version: '1.0.0'
main: com.aayan.albl.ALBLevel
api-version: '26.3'
depend: [ALBCore]

onEnable

override fun onEnable() {
    // Check first: if ALBCore failed to start, its classes can no longer be loaded.
    if (!server.pluginManager.isPluginEnabled("ALBCore")) {
        server.pluginManager.disablePlugin(this)
        return
    }
    val core = ALBCore.instance
    core.database.migrate(name) { /* tables, see Migrations */ }
    CommandUtil.registerCommand(this, "level") { /* ... */ }
    PAPIHook.register(this, "albskills", "total") { player -> totalOf(player).toString() }
}

Naming

All ALB plugins (ALBSkills, ALBItems, ALBDungeon, ALBQuests, ALBIslands, ALBChat, ALBRewards) share one database. Start every table name with the plugin's short name, so table("skills_players") becomes alb_skills_players, and use the plugin name as the migration owner. Publish placeholders under the plugin's own identifier, such as %albskills_total%.

Threading rules

The main thread runs the game. Anything slow on it (disk, network, database) makes the whole server lag. ALBCore is built so that you never have to block it.

APIRuns onCall from
Database query/update/transaction...ALBCore DB threadsany thread; returns CompletableFuture
Database.migratethe calling thread (blocking)onEnable only
PlayerData getters / setin memory, thread-safeany thread
PlayerData.fetch / editbackgroundany thread; returns a future
GUI, MessageUtil, ItemBuilder, Vaultmain threadmain thread
PAPIHook.register handlersany thread (TAB, scoreboards)must be thread-safe

To use a database result with the Bukkit API, hop back to the main thread with thenSync:

db.queryFirst("SELECT level FROM ${db.table("level_players")} WHERE uuid = ?", player.uniqueId) { it.getInt(1) }
    .thenSync(plugin) { level -> player.sendMessage("Level ${level ?: 1}") }
Never call .join() or .get() on a database future from the main thread. The one place blocking is fine is AsyncPlayerPreLoginEvent, which runs on a login thread.

Configuration

plugins/ALBCore/config.yml. Invalid values fall back to the default with a console warning. Database and player-data changes need a restart; /albcore reload applies webhooks, autosave interval and messages.

config-version: 1

database:
  type: sqlite                 # sqlite | mysql
  table-prefix: "alb_"         # letters, digits, _
  sqlite:
    file: "database.db"        # inside plugins/ALBCore/
  mysql:
    host: "localhost"
    port: 3306
    database: "minecraft"
    username: "root"
    password: ""
    use-ssl: false
    properties: {}             # extra JDBC properties, e.g. serverTimezone: "UTC"
  pool:                        # MySQL only; SQLite uses one connection
    maximum-pool-size: 10
    minimum-idle: 2
    connection-timeout-ms: 10000
    idle-timeout-ms: 600000
    max-lifetime-ms: 1800000
    keepalive-time-ms: 0

  storage: yaml                # yaml | sqlite | mysql
  autosave-interval-seconds: 300
  load-timeout-seconds: 10
  load-failed-message: "&cYour player data could not be loaded. Please try again in a moment."

discord:
  webhooks: {}

For extra YAML files in your own plugin, use ConfigFile. It copies the file from your jar on first use and falls back to the jar's values for keys the user's file is missing:

val levels = ConfigFile(this, "levels.yml")
val maxLevel = levels.config.getInt("max-level")
levels.reload()

Database

ALBCore.instance.database is one shared connection pool for ALBCore and every child plugin. The same code runs on SQLite (test servers) and MySQL (the real server).

Queries

val db = ALBCore.instance.database
val players = db.table("level_players")          // "alb_level_players"

db.update("UPDATE $players SET xp = xp + ? WHERE uuid = ?", 50, uuid)            // Future<Int>
db.query("SELECT uuid, level FROM $players ORDER BY level DESC LIMIT 10") { rs ->
    rs.getUuid("uuid") to rs.getInt("level")
}                                                                            // Future<List<Pair>>
db.queryFirst("SELECT level FROM $players WHERE uuid = ?", uuid) { it.getInt(1) } // Future<Int?>
db.batch("INSERT INTO $players (uuid, level) VALUES (?, ?)", rows)            // one transaction
db.insertAndGetKey("INSERT INTO ${db.table("logs")} (message) VALUES (?)", text) // Future<Long?>

db.transaction { conn ->                   // commit on return, rollback on throw
    conn.update("UPDATE $players SET coins = coins - ? WHERE uuid = ?", price, buyer)
    conn.update("UPDATE $players SET coins = coins + ? WHERE uuid = ?", price, seller)
}
  • Parameters are bound to ? in order. A UUID is stored as its 36-character string, an enum as its name, null as SQL NULL. Never build SQL by joining strings with player input.
  • Inside withConnection, transaction and migrations, use the blocking helpers on Connection: update, query, queryFirst, batch, insertAndGetKey, execute, inTransaction. On ResultSet there are getUuid, getIntOrNull and getLongOrNull.
  • Failures are logged by ALBCore (with the SQL) and complete the future exceptionally.
  • SQLite runs all tasks on one thread, in order. MySQL runs them in parallel: chain dependent steps with thenCompose or put them in one transaction.

Migrations

Each plugin declares its tables as numbered versions. ALBCore stores the version each plugin has reached in alb_schema_versions and runs only the missing steps, in order, each in its own transaction.

db.migrate("ALBLevel") {
    version(1, "Create players table") {
        execute("""CREATE TABLE ${table("level_players")} (
            uuid CHAR(36) NOT NULL PRIMARY KEY,
            level INT NOT NULL DEFAULT 1,
            xp BIGINT NOT NULL DEFAULT 0)""")
    }
    version(2, "Add prestige") {
        execute("ALTER TABLE ${table("level_players")} ADD COLUMN prestige INT NOT NULL DEFAULT 0")
    }
    version(3, "Backend-specific index") {
        mysql("CREATE INDEX ${table("lp_level")} ON ${table("level_players")} (level) USING BTREE")
        sqlite("CREATE INDEX ${table("lp_level")} ON ${table("level_players")} (level)")
    }
}
  • Call migrate in onEnable; it blocks until done. If it throws MigrationException, disable your plugin.
  • Never change or renumber a version that has run on a server. Add a new version instead.
  • MySQL commits CREATE/ALTER immediately, so a failed step can be half applied there. Keep one DDL statement per version. SQLite rolls back the whole step.
  • Servers sharing one MySQL database take a lock while migrating, so they never run the same step twice.

Player data

Simple per-player values: settings, counters, flags. Each player has one YAML document, stored where player-data.storage says. ALBCore loads it before the player joins and keeps it in memory. It saves in the background on autosave, on quit and on shutdown. If loading fails, the player is refused with a message instead of being let in with empty data.

PlayerData.getInt(player, "skills.mining.level", 1)
PlayerData.getString(player, "title", "none")            // also getLong/Double/Boolean/StringList/get/contains
PlayerData.set(player, "settings.mute-announcements", true)
PlayerData.set(player, "old.key", null)                   // removes
PlayerData.increment(player, "stats.kills")                  // atomic, returns the new value
PlayerData.of(player)?.keys("skills")                       // the PlayerDataHolder of a loaded player

// Any player, online or offline (async):
PlayerData.fetch(uuid).thenSync(plugin) { data -> show(data.getInt("level")) }  // offline copy is read-only
PlayerData.edit(uuid) { data -> data.increment("pending-rewards") }           // saved for offline players

Use your own table instead when you need to search or sort across players (leaderboards, island values) or store a lot per player.

Switching storage

  1. Set player-data.storage to the new type (for example mysql) and restart.
  2. Run /albcore playerdata import yaml (the old type). Offline players are copied; online players keep their current data.

If player-data.storage is a SQL type different from database.type, player data opens its own small connection pool with the same login settings.

GUI

GuiBuilder creates chest menus (1 to 6 rows). Chest menus work for Bedrock players through Geyser. Create a new GuiBuilder each time you open a menu for a player, and use it on the main thread.

val gui = GuiBuilder("&8Skills · &7%player_name%", 6)
gui.global {                                                   // on every page
        item(45) { _, ctx -> GuiItem(backArrow) { _, c -> c.previousPage() } }
        item(53) { _, ctx -> GuiItem(if (ctx.hasNextPage) nextArrow else filler) { _, c -> c.nextPage() } }
    }
    .page {                                                    // page 1
        item(10..16) { player, _ ->
            GuiItem(skillIcon(player)) { p, ctx -> levelUp(p); ctx.refresh() }
        }
    }
    .page { item(10) { _, _ -> GuiItem(moreIcon) } }          // page 2
    .setItem(49, { player -> closeButton(player) }) { player -> player.closeInventory() }
    .refreshEvery(20)                                          // ticks; only while open
gui.open(player)

Item-input slots

Everything in a GUI is locked except slots you open with allowItemPlacement. Shift-click, double-click, number keys, the offhand key and dragging are all checked against the slot filters.

val sell = GuiBuilder("&8Sell items", 4)
sell.allowItemPlacement(0..26) { item -> PriceRegistry.hasPrice(item.type) }
    .setItem(31, { sellButton }) { player -> sellAll(player, sell.getItems(0..26)); sell.clearItems(0..26) }
    .onClose { player -> player.inventory.addItem(*sell.getItems(0..26).toTypedArray()) }
sell.open(player)
Items in input slots stay in the GUI until you move them. Give them back in onClose, or they are lost.

Commands

Register commands in onEnable. They go through Paper's command system, so no plugin.yml entry is needed. Arguments are parsed first; the next word then picks a subcommand.

CommandUtil.registerCommand(this, "island") {
    aliases = mutableListOf("is")
    description = "Island commands"
    playerOnly = true
    action { sender, _ -> openIslandMenu(sender as Player) }   // "/island" with no subcommand

    subcommand("invite") {
        arg("player", ArgType.PLAYER)
        action { sender, args -> invite(sender as Player, args.player("player")) }
    }
    subcommand("setsize") {
        permission = "island.admin"                           // hidden from tab completion without it
        arg("owner", ArgType.OFFLINE_PLAYER)
        arg("size", ArgType.INT) {
            validate({ _, v -> v in 50..500) }) { MessageUtil.send(it, "&cSize must be 50-500") }
        }
        arg("reason", ArgType.TEXT) { optional = true }      // rest of the line
        action { sender, args ->
            setSize(args.offlinePlayer("owner"), args.int("size"), args.stringOrNull("reason"))
        }
    }
}
Arg typeValue
STRINGone word
TEXTthe rest of the line; must be the last argument
INT, LONG, DOUBLEnumbers
BOOLEANtrue/false, yes/no, on/off
PLAYERan online player by exact name (Bedrock names include the Floodgate prefix)
OFFLINE_PLAYERanyone who joined before; never blocks on a web lookup

Custom types: extend ArgType and read the value with args.get<T>(name).

object SkillArg : ArgType<Skill>("skill") {
    override fun parse(raw: String) = Skill.byId(raw)
    override fun suggestions() = Skill.ids
}

Per argument: optional, validate(check, onFail), suggest { }, onInvalid { sender, raw -> }. Per command: permission, playerOnly, noPermissionMessage, playerOnlyMessage, onMissingArgs, onUnknownSubcommand.

Hooks

PlaceholderAPI

PAPIHook.register(this, "albskills", "total") { player -> totalOf(player).toString() }  // %albskills_total%
PAPIHook.register(this, "level") { player -> PlayerData.getInt(player, "level", 1).toString() }  // %alb_level% (shared)
val text = PAPIHook.parse(player, "Balance: %vault_eco_balance%")

Each identifier becomes its own PlaceholderAPI expansion, created on first use. Identifiers use a-z and 0-9 only (PlaceholderAPI splits at the first _); keys use a-z, 0-9 and _. Handlers can be called from async threads, so only read thread-safe data. They are removed automatically when your plugin disables, and they survive /papi reload.

Vault

if (VaultHook.withdraw(player, 250.0)) { /* paid */ }
VaultHook.getBalance(player); VaultHook.has(player, 100.0); VaultHook.deposit(player, 50.0); VaultHook.format(1500.0)

Works with any economy registered through Vault or VaultUnlocked, even if it loads after ALBCore. Without an economy, reads return 0 and changes return false.

PacketEvents

if (PacketEventsHook.isEnabled()) PacketEventsHook.register(this, MyPacketListener())

Utilities

Text: ColorUtil and MessageUtil

All text accepts MiniMessage (<red>, <gradient:gold:red>) and legacy codes (&c, &l, &#ff8800, &x&f&f&8&8&0&0).

MessageUtil.send(sender, "&aSaved!")
MessageUtil.sendWithPAPI(player, "&7Rank: %luckperms_prefix%")
MessageUtil.actionBar(player, "&e+25 XP")
MessageUtil.sendTitle(player, "&6Level up!", "&7Level 12", fadeIn = 200, stay = 2000, fadeOut = 300)  // ms
MessageUtil.broadcast("&dA boss spawned!", permission = null)
val component = ColorUtil.parse("&bHello <bold>there")
val plain = ColorUtil.toPlainText("&bHello")                 // "Hello"
val safe = ColorUtil.escape(chatMessage)                         // player text: always escape
Never pass raw player text (chat, sign lines, renamed items) to parse without ColorUtil.escape. Otherwise players can inject tags such as click events.

Items and heads

val sword = ItemBuilder(Material.DIAMOND_SWORD)
    .name("&bStarter Sword")
    .lore("&7Damage: &c5", "&7Tier: &aE")
    .glow()
    .unbreakable()
    .data(key, PersistentDataType.STRING, "starter")
    .build()
val head = HeadUtil.fromBase64(texture)        // also fromPlayerName(name), fromPlayer(offlinePlayer)

Discord logging

Name your webhooks in ALBCore's config.yml, then send from any plugin. Requests run in the background, and mentions are always disabled so logged player text can never ping anyone.

discord:
  webhooks:
    staff:
      url: "https://discord.com/api/webhooks/..."
      username: "Skyabyss Logs"
DiscordLogger.on("staff").warning("Big trade", "${a.name} gave ${b.name} 64 diamonds")
DiscordLogger.on("staff").embed {
    title = "Boss killed"
    color = DiscordColor.PURPLE
    field("Floor", "E", inline = true)
    timestamp = true
}

Permission albcore.admin (operators by default).

Developing ALBCore

./gradlew build                 # tests + build/libs/alb-core-1.0.0.jar
./gradlew test                  # JUnit 6
./gradlew publishToMavenLocal   # API jar for child plugins
  • Database tests run on SQLite every time. Set ALBCORE_TEST_MYSQL_HOST (and optionally _PORT, _DATABASE, _USER, _PASSWORD) to run them against MySQL too. Use a throwaway database.
  • HikariCP is shaded and relocated. The Kotlin runtime is shaded but not relocated, so child plugins can share it. Paper already provides the MySQL/SQLite drivers, Gson and SLF4J.
  • When the public API changes, update MIGRATION.md, this page and .claude/skills/albcore/SKILL.md.

Upgrading from 0.1.0

1.0.0 renames a few classes and methods (PlayerDataUtil → PlayerData, AveragePrice → PriceRegistry, Vault method names, and more) and fixes several GUI exploits. The full list is in MIGRATION.md.
